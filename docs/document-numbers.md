# أرقام الفواتير (migration 0053)

## القواعد
- كل فاتورة بيع/شراء لها `invoice_number` دايمًا (NOT NULL وغير فارغ). القاعدة في الجدول نفسه (trigger)، فبتنطبق على أي مسار إدخال: RPC، service role، استيراد، كود مستقبلي.
- لو الخانة فاضية: النظام يولّد `S-000001` للبيع و`P-000001` للشراء، لكل مؤسسة، بدون فجوات، وآمن مع الطلبات المتزامنة. (تغيير الشكل: البادئتين `'S-'` و`'P-'` في `_next_document_number`.)
- لو المستخدم كتب رقم: يُحفظ كما كتب (بعد حذف المسافات). مرفوض التكرار: في البيع على مستوى المؤسسة، وفي الشراء على مستوى المورد (كل مورد له ترقيمه). المقارنة غير حساسة لحالة الحروف.
- الرقم لا يتعدّل بعد الإصدار.
- المرتجعات والمدفوعات والتحويلات وجرد المخزون **لا لها رقم خاص** بتصميم النظام؛ بتظهر برقم الفاتورة الأم.

## الفتح من الإشعار والبحث
- الروابط بالـ id مش بالرقم: `/dashboard/sales?inv=<id>` و`/dashboard/purchases?inv=<id>` و`/dashboard/warehouse-orders?tab=sales|purchase&status=all&inv=<id>`.
- trigger على جدول `notifications` يحوّل أي رابط بحث نصي `?q=` لفاتورة إلى رابط الـ id، فأي دالة إشعارات مستقبلية محمية.
- لو الفاتورة مش ظاهرة للدور (مثلاً مندوب آخر) تظهر رسالة "غير موجودة أو ليست ضمن ما يمكنك الاطلاع عليه".
- `global_search` بتعرض الرقم كعنوان وبترجّع الـ id، و`%` و`_` في اللي بتكتبه بيتعاملوا كحروف عادية.

## البيانات القديمة
- فقط الفواتير اللي بلا رقم أخدت أرقام، بترتيب الإنشاء. أي فاتورة عندها رقم لم تُمس، حتى لو مكررة.
- كل رقم اتولّد وقت الترحيل مسجّل في `invoice_number_backfill` (فاتورة، رقم، وقت). الفواتير دي كانت NULL قبل كده.
- الإشعارات القديمة: الرقم العشوائي اتبدل بالرقم الحقيقي والرابط بقى بالـ id.
